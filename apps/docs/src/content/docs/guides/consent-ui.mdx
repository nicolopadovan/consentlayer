ConsentLayer does not ship a consent banner, so its design, wording and
languages remain yours. This page documents `useConsentController()`, the hook
that provides a banner's state and actions, gives a complete banner and
settings dialog to copy into your app, and explains how to add consent
categories of your own. The recipe is the banner the
[Playground](/playground/) runs.

## `useConsentController()`

`useConsentController()` is exported from `consentlayer/react`. Its state is
held by `<AnalyticsProvider>`, so it must be called in a descendant of the
provider; elsewhere it throws
`useConsentController must be used within AnalyticsProvider`. Unlike
`useAnalytics()` and `useConsent()`, it has no fallback to the most recent
instance.

| Field | Type | Behaviour |
|---|---|---|
| `ready` | `boolean` | `false` until `analytics.consent.bootstrap()` has settled. Render nothing while it is `false`, so that returning visitors don't see the banner flash. |
| `error` | `string \| null` | The rejection reason, converted to a string, if `bootstrap()` rejected. The banner is then shown as if no consent were stored. |
| `bannerVisible` | `boolean` | After bootstrap, `true` when no consent is stored or the stored choice is [stale](#asking-again), and the provider's `autoShowBanner` prop is `true` (the default). |
| `dialogVisible` | `boolean` | Whether the settings dialog is open. Initially `false`. |
| `categories` | `readonly ConsentCategory[]` | The categories the dialog shows, from `analytics.consent.categories`: the built-in ones, then your custom ones. |
| `prefs` | `Record<ConsentCategory, boolean>` | The dialog's draft, one entry per category in `analytics.consent.categories`. Initialised from the stored consent, all `false` when there is none. |
| `setPrefs(next)` | `(next) => void` | Replaces the draft without saving it. |
| `acceptAll()` | `() => Promise<void>` | Grants every category, then hides the banner and the dialog. |
| `rejectNonEssential()` | `() => Promise<void>` | Denies every category, then hides both. |
| `savePreferences()` | `() => Promise<void>` | Saves `prefs`, then hides both. |
| `openDialog()`, `closeDialog()` | `() => void` | Show or hide the dialog. |
| `showBanner()`, `hideBanner()` | `() => void` | Show or hide the banner. |

The three saving actions call `analytics.consent.setConsent()` and hide the
banner and dialog only once it resolves, which is after the consent adapters
and the `server.consentEndpoint` request have finished.

<details>
<summary>Edge cases</summary>

- `prefs` is overwritten whenever the consent state changes, including
  changes made in another tab, by a consent adapter or by
  `analytics.consent.update()`. A draft the visitor has not saved is lost when
  that happens.
- The saving actions write only the toggleable categories. Because
  `setConsent()` replaces the whole state, a `sale_of_data` value set
  elsewhere is not kept.
- With `autoShowBanner={false}`, `bannerVisible` stays `false` until you call
  `showBanner()`, even for visitors who have not chosen.

</details>

### Reopening the settings

Visitors must be able to change their choice later. Inside React, call
`openDialog()`, as the recipe's "Cookie settings" button does below. Outside
React, for example in a footer rendered by a CMS, call the open-settings
global, which `<AnalyticsProvider>` defines when it mounts:

```html
<button type="button" onclick="window.CONSENTLAYER_openConsent?.()">Cookie settings</button>
```

The global's name follows [`names.prefix`](/guides/names/). With
`names.legacy`, `ACM_openConsent` is defined as well. The
`openConsentGlobalKey` prop of `<AnalyticsProvider>` replaces both with the
name you pass.

### Asking again

A stored choice does not expire by default. Two options of
`createAnalytics({ consent })` make ConsentLayer ask the visitor again:

- **`maxAgeDays`** makes a choice stale once it is older than that many days.
  The CNIL, for example, recommends asking again after six months.
- **`policyVersion`** makes a choice stale when it was made under another
  major version of your privacy policy: the part before the first `.`.

```ts title="lib/analytics.ts"
export const analytics = createAnalytics({
  providers,
  consent: { maxAgeDays: 180, policyVersion: POLICY_VERSION },
})
```

Version your privacy policy as `major.minor` and keep the version in one
constant that the browser and the [consent route](/guides/consent-records/#the-consent-route)
both import:

```ts title="lib/policy.ts"
export const POLICY_VERSION = '3.2'
```

Raise the major version when the policy changes in a way visitors must agree
to again, such as a new purpose or a new recipient of their data. Raise the
minor version for edits that need no new consent, such as a new contact
address:

| Change | Visitors asked again | New records cite |
|---|---|---|
| `'3.1'` to `'3.2'` | No | `'3.2'` |
| `'3.2'` to `'4.0'` | Yes | `'4.0'` |

A choice made under `'3.1'` stays valid under `'3.2'`, and its record keeps
citing `'3.1'`, the version the visitor agreed to. A version without a `.`,
such as a date like `'2026-10-01'`, is entirely the major version, so any
change asks again.

Each choice is stored with the date it was made and the `policyVersion` in
effect. When `bootstrap()` finds a stale choice, `bannerVisible` becomes
`true` and `analytics.consent.isStale()` returns `true`. What the stale choice
means until the visitor answers depends on `onStale`:

| `onStale` | Consent until the visitor chooses | Providers |
|---|---|---|
| `'discard'` (default) | `null`, as for a first visit | Only those with `requiredConsent: 'none'` run. |
| `'keep'` | The stale choice | Unchanged. The banner is shown on top. |

With `'keep'`, `prefs` starts from the stale choice, so a visitor who confirms
it without changes stores the same choice again. That confirmation counts as a
new choice: it is stored with the current date and `policyVersion` and, with
`server.consentEndpoint`, recorded again on the server.

<details>
<summary>Choices stored without a date or version</summary>

A choice stored before these options existed, or before you first set them,
carries no date or no `policyVersion`. It counts as stale for each option you
set, so turning on `maxAgeDays` or `policyVersion` asks every returning
visitor once. Choices supplied by a consent adapter, such as Shopify Customer
Privacy, are stored with the current date and version, since the adapter is
their source.

</details>

Render the banner once inside the provider, and give visitors a way back to
the settings:

```tsx title="components/analytics-shell.tsx"
'use client'

import { AnalyticsProvider, useConsentController } from 'consentlayer/react'
import type { ReactNode } from 'react'
import { analytics } from '../lib/analytics'
import { ConsentBanner } from './consent-banner'

function CookieSettingsButton() {
  const { openDialog } = useConsentController()
  return (
    <button type="button" onClick={openDialog}>
      Cookie settings
    </button>
  )
}

export function AnalyticsShell({ children }: { children: ReactNode }) {
  return (
    <AnalyticsProvider analytics={analytics}>
      {children}
      <ConsentBanner privacyPolicyUrl="/privacy" />
      <CookieSettingsButton />
    </AnalyticsProvider>
  )
}
```

In a Next.js app, import `AnalyticsProvider` from `consentlayer/next` instead
so page views follow navigation, as shown in [Next.js](/start/nextjs/). The banner's text is plain strings in your
component, so translate it with the i18n library your app already uses.

## Custom categories

`preferences`, `analytics` and `marketing` are built in. To add your own,
declare it in the `ConsentCategories` interface and pass it to
`createAnalytics()`:

```ts title="lib/analytics.ts"
import { createAnalytics, definePlugin, loadScript } from 'consentlayer'

declare module 'consentlayer' {
  interface ConsentCategories {
    functional: true
  }
}

const supportChat = definePlugin({
  id: 'support-chat',
  requiredConsent: 'functional',
  load: () => loadScript('https://chat.example.com/widget.js'),
})

export const analytics = createAnalytics({
  categories: ['functional'],
  providers: [supportChat],
})
```

A custom category behaves like a built-in one. It is denied until granted,
stored, broadcast and posted to the `server.consentEndpoint`. "Accept all"
grants it and "Reject non-essential" denies it. `analytics.consent.categories`
lists it after the built-in categories, in the order of the `categories` option, and the
recipe's dialog shows a toggle for it in that order. Any plugin can require it
with `requiredConsent`.

Both steps are needed. Without the declaration, `categories: ['functional']`
and `requiredConsent: 'functional'` don't compile. Without the `categories`
option, the category is dropped whenever consent is normalised, so it is never
stored and a plugin that requires it never loads.

If you record consent on the server, pass the same list to
`createConsentHandler({ categories })`. The handler otherwise drops the custom
categories from the record. See [Consent records](/guides/consent-records/).
